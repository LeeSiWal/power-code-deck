# 승인 허용 목록 ("앞으로도 허용") 설계

- 작성일: 2026-07-27
- 상태: 구현됨 (v0.6.0)
- 로드맵: `ROADMAP.md` 2번

## 배경

모든 승인이 일회성입니다. `go test ./...`을 허용해도 다음에 또 묻습니다. 반복되는 빌드·테스트·린트 명령마다 승인 카드가 뜨는 것이 지금의 주된 성가심입니다.

승인 게이트 자체는 정상 동작합니다 — 문제는 **같은 결정을 반복해야 한다는 것**입니다.

## 확인된 사실

**① 끼워 넣을 지점이 정확히 하나입니다.**
`services/permission_policy.go`의 `autoDecide(mode, tool, input, cwd)`. 사람에게 묻기 전 모든 게이트 호출이 여기를 지나며, 규칙 검사에 필요한 값(도구·입력·작업 디렉토리)이 모두 여기 있습니다.

**② "같은 호출"을 식별할 수단이 지금 없습니다.**
요청 id는 CLI의 `tool_use_id`이고 **매 호출마다 새로 생성됩니다**. 따라서 규칙 키를 이 설계가 정의해야 합니다.

**③ 프로젝트 단위 저장소가 없습니다.**
설정은 `agents` 테이블의 에이전트별 컬럼뿐입니다. 다만 `working_dir`로 묶는 관례는 이미 있습니다 — `AgentService.inheritedNativeConfig`가 같은 작업 디렉토리의 에이전트끼리 모델·모드를 물려줍니다.

**④ 기존 안전 분류기를 재사용할 수 있습니다.**
`isSafeToolCall` / `isSafeBash`가 위험 명령(`rm`·`sudo`·`git push` 등)과 위험 구문을 이미 판정합니다.

## 목표

- 반복되는 동일 명령을 한 번 허용하면 다시 묻지 않는다
- 어떤 규칙이 저장돼 있는지 사용자가 확인하고 지울 수 있다
- 규칙이 승인 게이트를 무력화하지 않는다

## 비목표 (YAGNI)

- 패턴/와일드카드 규칙 (`npm *`) — §3 참고
- "앞으로도 거부" — 거부는 보통 일회성 판단이고, 영구 거부가 필요한 상황이 관찰된 적 없음
- 규칙 만료 기한
- 규칙 가져오기/내보내기, 팀 간 공유
- Claude CLI 자체의 `settings.json` 권한 규칙과의 연동 — 우리 게이트는 서버 측이며 별개다

## 결정 요약

| 항목 | 결정 |
|---|---|
| 기억 단위 | **정확한 명령/대상** (정규화 후 완전 일치) |

## 1. 규칙 키 — 무엇을 정확히 기억하나

규칙은 `(working_dir, tool_name, target)` 세 값으로 식별합니다.

`target`은 도구에 따라 다릅니다:

| 도구 | `target` | 정규화 |
|---|---|---|
| `Bash`, `BashOutput` | `input.command` | 앞뒤 공백 제거, 연속 공백을 하나로 |
| `Write`, `Edit`, `MultiEdit`, `NotebookEdit` | `input.file_path` \| `notebook_path` \| `path` | 절대 경로로 변환 후 `filepath.Clean` |
| 그 외 | 빈 문자열 | — |

`target`이 빈 문자열인 도구는 **도구 이름만으로 규칙이 성립**합니다. 이는 의도된 것입니다 — 그런 도구는 대상 개념이 없어 도구 단위가 곧 최소 단위입니다.

**정규화는 최소한만 합니다.** 공백 정리와 경로 정리 이상은 하지 않습니다. 규칙 매칭이 영리해질수록 "내가 무엇을 허용했는지"를 예측할 수 없게 되고, 예측할 수 없는 규칙은 감사할 수 없습니다.

### 왜 패턴이 아닌가

`npm *` 같은 패턴은 덜 귀찮지만 두 가지가 걸립니다. 첫째, 패턴 언어를 만들어야 하고 **권한 결정에서 사고가 나는 지점이 정확히 거기**입니다. 둘째, `npm test`를 허용한 사용자가 `npm publish`까지 허용했다고 생각하지 않습니다.

실제 성가심의 대부분은 **반복되는 동일 명령**입니다 — `go test ./...`, `npm run build`, `tsc --noEmit`, `git status`. 반면 `git commit -m "..."`처럼 인자가 매번 다른 호출은 오히려 확인해야 하는 쪽입니다. 완전 일치는 전자를 정확히 잡고 후자는 건드리지 않습니다.

## 2. 적용 범위 — 프로젝트

규칙은 `working_dir`에 매입니다. "이 레포에서는 `npm test`를 믿는다"가 사람이 신뢰를 형성하는 단위이고, 세션을 지우고 다시 만들어도 규칙이 살아남아야 유용합니다.

전역 범위는 채택하지 않습니다 — 한 레포에서 믿고 허용한 명령이 낯선 레포에서도 자동 실행되는 것은 놀라운 동작입니다.

`working_dir`로 묶는 것은 새 발명이 아니라 `inheritedNativeConfig`가 이미 쓰는 관례를 따르는 것입니다.

## 3. 위험 명령은 규칙이 될 수 없다

`isSafeToolCall`이 안전하지 않다고 판정한 호출에는 **"앞으로도 허용"을 제공하지 않습니다.** 일회 허용은 그대로 가능합니다.

`rm -rf`, `sudo …`, `git push`에 영구 규칙을 허용하면 승인 게이트를 만든 이유가 사라집니다. 게이트의 존재 목적이 정확히 그런 호출을 사람 눈앞에 세우는 것입니다.

이 판정은 **저장 시점과 적용 시점 양쪽에서** 수행합니다. 저장 시점 검사만 두면, 나중에 위험 목록이 넓어졌을 때 이미 저장된 규칙이 그 확장을 우회합니다.

## 4. 결정 흐름

```
게이트 호출 도착
   ↓
autoDecide(mode, tool, input, cwd)
   ├─ bypassPermissions      → 허용
   ├─ auto + isSafeToolCall  → 허용
   ├─ ★ 규칙 일치 + 여전히 안전  → 허용      ← 이번 추가
   └─ 그 외                   → 사람에게
```

규칙 검사는 **기존 모드 정책 다음**에 놓습니다. 모드가 이미 허용하는 경우 규칙을 볼 이유가 없고, 순서를 뒤집으면 `plan` 모드에서도 규칙이 발동해 모드의 의미가 무너집니다.

**규칙은 모드를 이기지 않습니다.** `plan` 모드에서는 규칙이 있어도 실행하지 않습니다 — 플랜 모드의 약속은 "실행하지 않는다"이고, 규칙이 그것을 뒤집으면 모드를 신뢰할 수 없게 됩니다.

## 5. 저장소

새 테이블. 기존 마이그레이션 관례(비치명적 `db.Exec`)를 따릅니다.

```sql
CREATE TABLE IF NOT EXISTS approval_rules (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    working_dir TEXT NOT NULL,
    tool_name   TEXT NOT NULL,
    target      TEXT NOT NULL DEFAULT '',
    created_at  TEXT DEFAULT (datetime('now')),
    UNIQUE(working_dir, tool_name, target)
);
```

`UNIQUE` 제약이 중복 저장을 막습니다 — 같은 규칙을 두 번 만들면 조용히 무시됩니다(`INSERT OR IGNORE`).

에이전트에 외래키를 걸지 않습니다. 규칙은 프로젝트에 속하며 에이전트보다 오래 삽니다.

## 6. UI

### 승인 카드

기존 `허용` / `거부` 옆에 **`항상 허용`**을 추가합니다. 위험 판정된 호출에는 이 버튼을 렌더하지 않습니다.

버튼에는 무엇이 저장되는지가 보여야 합니다. 눌렀을 때 무엇이 허용되는지 모르면 신뢰할 수 없는 결정이 됩니다:

```
[허용]  [항상 허용]  [거부]
        └ 이 프로젝트에서 `go test ./...` 를 다시 묻지 않습니다
```

두 곳 모두에 넣습니다 — 세션 안의 `NativeChat` 승인 카드와 관제실의 `ApprovalFeed`. 승인은 어느 쪽에서든 처리할 수 있어야 하고, 한쪽에만 있으면 "왜 여기선 안 되지"가 됩니다.

### 규칙 관리

설정 화면에 목록을 둡니다 — 프로젝트별로 묶어 도구·대상·생성 시각을 보여주고 개별 삭제. **저장한 규칙을 볼 수 없으면 안 됩니다.** 확인할 수 없는 권한 부여는 시간이 지나면 위험 요소가 됩니다.

## 7. 전송

`NativeDecidePayload`에 필드 하나를 더합니다:

```go
Remember bool `json:"remember,omitempty"`
```

`omitempty`이므로 낡은 클라이언트는 영향받지 않습니다. 서버는 `Behavior == "allow" && Remember` 일 때만 규칙을 저장하며, 저장 전에 §3의 안전 판정을 다시 확인합니다.

## 8. 에러 처리

- 규칙 저장 실패(DB 오류)는 **승인 자체를 실패시키지 않습니다.** 허용은 그대로 진행하고 규칙만 남지 않습니다 — 부가 기능이 주 기능을 막으면 안 됩니다
- `target` 추출 실패(입력 모양이 다름)는 규칙을 저장하지 않습니다. 빈 `target`으로 저장하면 도구 전체를 허용하는 규칙이 되어 사용자가 의도한 것보다 훨씬 넓어집니다
- 규칙 조회 실패는 "규칙 없음"으로 처리합니다 — 사람에게 묻는 쪽으로 실패합니다

## 9. 검증

- 서버 테스트:
  - 규칙 일치 시 허용, 불일치 시 사람에게
  - **위험 명령은 규칙이 있어도 사람에게** (적용 시점 재검사)
  - **위험 명령은 저장되지 않음** (저장 시점 검사)
  - 다른 `working_dir`의 규칙은 적용되지 않음
  - `plan` 모드에서는 규칙이 있어도 실행하지 않음
  - 정규화: `  go   test  ` 와 `go test`가 같은 규칙에 걸림
  - `target` 추출 실패 시 저장 안 함
- `cd server && CGO_ENABLED=0 go build ./... && go test ./...`
- `cd client && ./node_modules/.bin/tsc --noEmit`
- 실제 렌더 확인:
  - `go test ./...` 을 `항상 허용` → 같은 명령 재실행 시 카드가 안 뜨는지
  - 인자가 다른 명령(`go test ./services/`)은 여전히 묻는지
  - `rm -rf /tmp/x` 승인 카드에 `항상 허용` 버튼이 **없는지**
  - 설정에서 규칙이 보이고 삭제되는지, 삭제 후 다시 묻는지
- `dist/pcd.exe` 재빌드

## 10. 리스크

| 리스크 | 대응 |
|---|---|
| 규칙이 쌓여 무엇을 허용했는지 모르게 됨 | 설정의 관리 화면이 필수 범위. 프로젝트별 그룹핑 |
| 위험 목록이 나중에 넓어질 때 기존 규칙이 우회 | 적용 시점에도 안전 판정을 재수행 |
| 완전 일치라 기대만큼 안 줄어듦 | 실사용 후 판단. 넓히는 것은 되돌리기 쉽지만 좁히는 것은 어렵다 — 좁게 시작한다 |
| `working_dir` 문자열이 미묘하게 달라 규칙이 안 맞음 | 저장·조회 모두 `filepath.Clean`을 거친 값으로 통일 |
