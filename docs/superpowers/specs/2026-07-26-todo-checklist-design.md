# 할일 체크리스트 설계

- 작성일: 2026-07-26
- 상태: 구현됨 (v0.5.0)
- 로드맵: [ROADMAP.md](../../../ROADMAP.md) 6번의 절반. 나머지 절반(관제실 활동 표시)과 같은 트랜스크립트 파이프라인을 쓴다.

## 배경

Claude Code는 작업을 계획할 때 `TodoWrite` 도구로 체크리스트를 만들고 갱신한다. 이 리포에는 그것을 다루는 코드가 **전혀 없다** — 일반 도구로 흘러가 승인 정책(`permission_policy.go:46`, 안전 목록)과 활동 스프라이트(`activityVisual.ts:23-25`, `think`)에만 이름이 등장할 뿐, 입력을 파싱하지도 화면에 띄우지도 않는다.

그런데 이 체크리스트는 **에이전트가 스스로 만드는 가장 읽기 쉬운 진행 상황**이다. 지금 사용자는 "얘가 지금 뭘 하고 있고 얼마나 남았나"를 알려면 채팅을 거슬러 읽어야 한다.

## 확인된 데이터 사실

추측이 아니라 이 머신의 실제 트랜스크립트 143개를 스캔해 확인했다 (`TodoWrite` 호출 129회).

```
tool_use { type, id, name:"TodoWrite", input:{ todos:[…] }, caller }
todo     { content, status, activeForm }
status ∈ pending | in_progress | completed
record   { parentUuid, isSidechain, message, requestId, type, uuid,
           timestamp, effort, userType, entrypoint, cwd, sessionId, version, gitBranch }
```

**핵심: 매 호출이 전체 스냅샷이다 — 델타가 아니다.** 한 세션에서 1회차 7개 → 2회차 16개로 늘면서 첫 항목의 문구까지 `[감사 완료] …`로 다시 쓰인 것을 확인했다. Claude는 목록을 통째로 다시 쓴다.

이 사실 하나가 설계를 크게 단순화한다: **마지막 `TodoWrite`가 곧 현재 상태이며, 병합 로직이 필요 없다.**

`activeForm`은 진행 중일 때 보여주라고 있는 필드다 (`"퍼센타일 분포 재생성 중"`).

## 목표

- 세션을 보고 있을 때 "지금 무엇을, 몇 개 중 몇 번째"가 찾아보지 않아도 보이게 한다
- 계획이 어떻게 바뀌어왔는지를 대화 스크롤에서 되짚을 수 있게 한다
- 터미널(PTY) 세션에서도 동작하게 한다

## 비목표 (YAGNI)

- 사용자가 할일을 직접 편집·추가·체크하는 기능 (이 목록은 에이전트의 것이다)
- 할일 이력의 별도 저장·검색 (트랜스크립트가 이미 원본이다)
- 세션 간 할일 집계
- 서브에이전트의 할일을 따로 보여주기

---

## 1. 어디서 파싱하나 — 서버, `services/activity.go`

`ActivityManager`가 이미 `~/.claude/projects/<encoded-cwd>/*.jsonl`을 800ms마다 폴링하며 `tool_use` / `tool_result` 블록을 파싱하고 있다. 여기에 `TodoWrite` 처리를 얹는다.

**서버에서 파싱하는 이유:**

- 그 파일을 이미 읽고 있으므로 **새 I/O가 0이다**
- **PTY 세션에서도 동작한다** — Claude Code는 우리가 stream-json으로 구동하든 사용자가 터미널 TUI를 쓰든 트랜스크립트를 남긴다. 클라이언트에서 네이티브 이벤트 스트림을 파싱하면 네이티브 챗에서만 되고, 재접속 시 히스토리 재생에 의존하게 된다
- 재접속·다른 기기 접속 시 현재 상태를 다시 계산할 필요 없이 그대로 내려줄 수 있다

## 2. 반드시 피해야 할 함정 두 개

이 두 가지는 순진하게 구현하면 반드시 밟는다.

### ① 20초 stale 정리에 태우면 안 된다

`activity.go`는 활동 노드를 마지막 활동 후 일정 시간(현재 20초)이 지나면 정리한다. **할일 목록은 그 수명을 따르면 안 된다** — 에이전트가 잠깐 생각하거나 사용자 입력을 기다리는 동안 체크리스트가 사라지기 때문이다.

할일 스냅샷은 **새 `TodoWrite`가 오거나 세션이 끝날 때까지 유지**된다. 활동 노드와 다른 생명주기를 갖는다는 점을 코드에 명시한다.

### ② 서브에이전트의 `TodoWrite`를 걸러야 한다

서브에이전트(Task/Agent 도구로 생성된 것)도 자기 `TodoWrite`를 호출한다. "마지막 호출이 이긴다"를 그대로 적용하면 **서브에이전트의 목록이 메인 목록을 덮어쓴다.**

레코드에 `isSidechain` 필드가 있는 것을 확인했다. **메인 체인(`isSidechain: false`)의 호출만** 반영한다. 서브에이전트 할일을 따로 보여주는 것은 비목표다.

## 3. 어떻게 전달하나

`agent:activity`는 `BroadcastToAgent` + `watchingAgent` 필터를 타는 **세션 스코프** 이벤트다. 관제실은 어떤 세션도 watch하지 않으므로 이 경로로는 관제실에 닿지 않는다.

따라서 두 단위로 나눈다. 타협이 아니라 이것이 맞다 — 벽은 밀도를, 세션은 상세를 원한다.

| 단위 | 내용 | 경로 |
|---|---|---|
| 상세 | 전체 목록 (`content`, `status`, `activeForm`) | 세션 스코프 활동 스냅샷 |
| 요약 | 완료/전체 개수 + 진행 중 항목 한 줄 | 관제실 요약 (`control_room.go`, BroadcastAll) |

두 경로 모두 **같은 파서**(§1)의 결과를 쓴다. 요약은 상세에서 파생될 뿐 별도 계산이 없다.

## 4. 화면 — A(스트립) + C(인라인)

두 가지를 모두 넣는다. 중복이 아니라 **역할이 다르다**: 스트립은 "지금 상태", 인라인 카드는 "이 시점에 계획을 다시 짰다"는 기록이다.

### A. 상시 스트립 (터미널 화면)

```
┌────────────────────────────────────────────┐
│ ☑ 3/7  ▸ 퍼센타일 분포 재생성 중        [∨] │  ← 항상 보임
├────────────────────────────────────────────┤   (탭하면 펼침)
│ ✓ 타이밍 섹션 감사                          │
│ ✓ 엔진 버그 수정                            │
│ ▸ 퍼센타일 분포 재생성 중                   │
│ ○ relationType 하드코딩 제거                │
└────────────────────────────────────────────┘
```

- 접힌 상태: 완료/전체 개수 + 진행 중 항목의 `activeForm`
- 탭하면 전체 목록 펼침. 펼침 여부는 클라이언트 로컬 상태
- **할일이 없으면 스트립 자체를 렌더하지 않는다** (빈 껍데기 금지)

우측 패널 탭으로 넣지 않는 이유: 이 기능의 목적이 "찾아보지 않아도 알게 하는 것"인데, 열어야 보이는 탭은 그 목적을 스스로 무너뜨린다. 대가는 모바일 세로 공간 한 줄이며, 이를 받아들인다.

### C. 채팅 인라인 카드

`TodoWrite`는 이미 네이티브 챗에 도구 카드로 렌더된다. 이것을 할일 전용 표현으로 바꾼다.

**반드시 접힌 형태가 기본이어야 한다.** 16개짜리 목록이 재계획마다 통째로 들어가면 대화를 읽을 수 없게 된다. 기본은 `할일 16개 · 완료 1` 한 줄이고, 탭하면 펼친다.

### 관제실 타일 (한 줄)

```
☑ 3/7 · 퍼센타일 분포 재생성 중
```

완료/전체 + 진행 중 항목의 `activeForm`. 한 줄, 접기 없음, 클릭 없음 — 벽은 읽는 곳이지 조작하는 곳이 아니다. 할일이 없으면 이 줄을 렌더하지 않는다.

**이 줄이 들어가는 자리는 방금 리스닝 포트를 걷어낸 자리다.** 포트는 두 가지 이유로 표시할수록 해로웠다: `port_scanner.go`의 `Poll(agentID)`이 `ss -tlnp`로 머신 전체를 훑은 뒤 `agentID`를 캐시 키로만 쓰고 필터링에 쓰지 않아 모든 에이전트가 동일한 시스템 전역 목록(실측 25개, pcd 자신·ssh·postgres 포함)을 받았고, 링크의 `http://localhost:PORT`는 도메인으로 접속한 기기에서 그 기기 자신을 가리켰다.

그 자리에 터미널 썸네일을 넣는 안은 기각했다 — 이유는 §부록 참고.

## 5. 왜 관제실 타일을 함께 하나

원래 이것을 2단계로 미뤘으나 이번 범위로 합친다.

- **추가 비용이 작다.** 파서(§1)와 필터·수명 규칙(§2)이 이미 필요하고, 요약은 그 결과에서 개수와 진행 중 항목을 뽑는 것뿐이다. `AgentSummary`에 필드 세 개를 더하는 것이 실질 증분이다.
- **채워야 할 자리가 생겼다.** 포트를 걷어내 타일에 빈 줄이 생겼고, 벽에서 "이 세션이 지금 뭘 하는지"를 알려주는 신호가 `lastTool` 말고는 없다. `lastTool`은 `Edit`처럼 도구 이름일 뿐이라 의미를 전달하지 못한다.
- **두 표면을 따로 만들면 파서를 두 번 검증하게 된다.** 함정 두 개(§2)는 어느 표면에서든 동일하게 밟는다.

## 6. 에러 처리

- `input.todos`가 없거나 모양이 다르면 그 호출을 **무시**하고 직전 스냅샷을 유지한다. CLI가 스키마를 바꿔도 화면이 깨지지 않고 낡은 상태로 남을 뿐이다
- 할일이 하나도 없으면 스트립·카드 모두 렌더하지 않는다
- 진행 중(`in_progress`) 항목이 없으면(전부 완료 또는 전부 대기) 스트립은 개수만 보여준다

## 7. 검증

- 서버: `TodoWrite` 파싱 단위 테스트 — 전체 덮어쓰기, `isSidechain: true` 무시, 잘못된 모양 무시, 20초 idle 후에도 목록 유지
- `cd server && CGO_ENABLED=0 go build ./... && go test ./...`
- `cd client && ./node_modules/.bin/tsc --noEmit`
- 실제 렌더 확인:
  - 할일이 있는 세션에서 스트립이 뜨고 진행 중 항목이 `activeForm`으로 보이는지
  - 에이전트가 20초 이상 조용해도 스트립이 **사라지지 않는지** (함정 ①)
  - 서브에이전트를 쓰는 작업에서 메인 목록이 덮어써지지 않는지 (함정 ②)
  - 할일이 없는 세션에 빈 스트립이 안 뜨는지
  - 채팅 인라인 카드가 접힌 상태로 시작하는지
  - **관제실 타일에 `☑ 3/7 · …`이 뜨는지** — 세션을 열지 않은 상태에서 확인할 것. 여기서 비어 있으면 요약이 아니라 세션 스코프 경로를 탄 것이다(§3)
  - 할일이 없는 세션의 타일에는 그 줄이 없는지
- `dist/pcd.exe` 재빌드 (클라이언트 변경)

## 8. 리스크

| 리스크 | 대응 |
|---|---|
| CLI가 `TodoWrite` 입력 스키마를 바꾸면 조용히 빈 목록이 된다 | 파싱 실패 시 직전 상태 유지 + 도구 이름을 상수로 분리. 타입 검사로는 안 잡히므로 검증 항목에 포함 |
| 스트립이 모바일 세로 공간을 먹는다 | 접힌 상태는 한 줄. 할일이 없으면 렌더하지 않음. 실사용 후 조정 |
| 활동 스냅샷이 커진다 (800ms마다 전송) | 할일은 목록이 바뀔 때만 갱신되므로 대부분 동일 내용의 재전송이다. 실측 후 필요하면 변경 시에만 싣는 방식으로 조정 |

## 부록 A: 왜 터미널 썸네일이 아닌가

포트를 걷어낸 자리에 터미널 썸네일(`TerminalSnapshot`)을 넣는 안이 나왔고, 기각했다. 두 가지가 각각 독립적으로 이 안을 막는다.

1. **네이티브 세션에는 PTY가 없다.** `services/claude_driver.go:14`가 명시한다 — *"no PTY, no VT emulation, no screen to replay"*. Claude 세션은 네이티브 챗이 기본이므로 대부분의 타일이 영구 빈 화면이 된다.
2. **`terminal:output`은 세션 스코프다** (`ws/hub.go:705`, `BroadcastToAgent`). 관제실은 어떤 세션도 watch하지 않으므로 애초에 이 이벤트를 받지 못한다.

이 둘은 v0.4.0에서 타일의 `SubAgentBar`를 제거한 이유와 **정확히 같은 실패 모드**다. 같은 실수를 반복하지 않기 위해 기록한다.

할일 요약은 이 두 문제가 모두 없다: 트랜스크립트에서 나오므로 PTY 여부와 무관하고, 관제실 요약(`BroadcastAll`)으로 내려가므로 구조적으로 도달한다. 읽히기도 더 낫다 — 80칼럼 터미널 화면은 타일 크기에서 읽을 수 없지만 `☑ 3/7 · 퍼센타일 분포 재생성 중`은 읽힌다.

## 부록 B: 왜 클라이언트 파싱이 아닌가

네이티브 챗의 `foldEvents()`가 이미 `tool_use` 블록을 보고 있어 클라이언트 파싱이 더 싸 보인다. 그러나:

- PTY(터미널) 세션에는 그 이벤트 스트림이 없다
- 재접속 시 히스토리 재생에 의존해야 하고, 히스토리는 상한이 있다(`maxNativeHistory`)
- 관제실 요약(§4)에는 어차피 서버 데이터가 필요하다

서버에서 한 번 파싱하면 세 경우가 모두 해결된다.
